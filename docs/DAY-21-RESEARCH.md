# Day 21 — The Chainless Traveler / Layover

Research performed October 21, 2026 before implementation. Primary requirements: complete master build specification and complete Day 21 prompt in `prompts/dapp-prompts.ts`. The live [Day 21 challenge](https://www.dapptober.xyz/dapp/21) was read in Codex's browser; it confirms unified balances, agent route selection/explanation, sponsored gas and a departures board. Its optional Jev layer is included. The supplied `2026SocialPosts/33-day-21.png` inspired the copper airport lounge, split-flap typography and boarding-pass interaction; original preserved.

## Protocol decisions

- [thirdweb Bridge payment guide](https://portal.thirdweb.com/bridge/send): `Bridge.Buy.prepare` specifies destination output amount, sender and receiver. A prepared quote is not a delivery. Origin transactions and approvals are normalized, bounded, pinned and reviewed before signing. The installed SDK's `Buy`, `Quote`, `Route` and `Status` declarations were inspected. Quote expiry is milliseconds; the app caps freshness at 60 seconds. No unquoted testnet bridge route is promised.
- [thirdweb smart accounts](https://portal.thirdweb.com/typescript/v5/smartWallet) and [EIP-1193 adapter](https://portal.thirdweb.com/typescript/v5/eip1193/fromProvider): browser-owned smart accounts with `sponsorGas:true`. A project must actually approve/fund sponsorship on every enabled source. No server private spending key and no native-gas fallback are introduced. Each user-signed operation is bound to the saved transaction; receipt checks understand that a bundler, not the account, is the top-level sender.
- [LI.FI quote API](https://docs.li.fi/api-reference/get-a-quote-for-a-token-transfer), [canonical API index](https://docs.li.fi/llms.txt) and [status API](https://docs.li.fi/api-reference/check-the-status-of-a-cross-chain-transfer): use fixed official REST URLs and optional Partner Portal key. The exact-input quote is an alternative for swaps only; USDC pay/mint funding uses exact-output thirdweb or direct delivery. `DONE/PARTIAL` and `DONE/REFUNDED` require review, not a green arrival. `NOT_FOUND` remains pending. Returned chain/token/sender/receiver/input/minimum metadata are checked. LI.FI router calldata is reviewed provider-generated data; code pins do not prove proxy implementation immutability or economic semantics.
- [Across Swap API](https://docs.across.to/introduction/swap-api) was reviewed. Direct Across integration was not added: thirdweb plus LI.FI already covers the selected adapter boundary. Do not confuse Across's legacy suggested-fees endpoint with its current swap transaction API.

## Network and authority

The destination is Base Sepolia (84532) for testing and Base (8453) for production. A test configuration cannot include mainnet funding chains. Mainnet may add Ethereum, Optimism and Arbitrum as funding sources; their smart accounts and canonical six-decimal USDC must be explicitly configured. Those source networks do not change where the app/pass is deployed. Missing market liquidity or testnet protocol support blocks a route rather than moving the chosen network.

Balances are USDC units from configured smart accounts, not a dollar valuation or a wallet's entire net worth. Partial RPC reads remain visibly unavailable. There is no agent signing/session authority: every allowance, payment, swap and mint requires the user's smart-account signature. The fixed-price pass enforces its one-USDC payment onchain. If autonomous spending is added later it must use reviewed onchain budgets/session limits, not this app's offchain per-itinerary limits.

User intent is a deliberately small typed grammar. Jev can choose only a validated candidate ID and small/large explanation model with confidence at least 0.9. The LLM explains immutable economics and cannot rewrite a transaction. Signed approvals are exact, never unlimited. The app accepts only zero-native-value source calls and a single bridge step. Arrival requires provider binding plus the actual destination token Transfer receipt with three confirmations; mint additionally requires the expected ERC721 mint event. Three confirmations reduce ambiguity; they are not economic finality for a rollup.
