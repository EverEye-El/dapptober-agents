# Day 26 research — Credentialed Studio

Read the complete master specification and canonical Day 26 prompt before implementation. Inspected `2026SocialPosts/38-day-26.png` and the live [challenge](https://www.dapptober.xyz/dapp/26) in the Codex browser. The title, film-backlot vibe, feature list and “images or clips” option match. Live Jev is optional there; the canonical feature requests it, so real creation/upload/mint uses a separate fail-closed typed Jev gate.

Primary technical sources checked:

- [Official C2PA JavaScript SDK](https://github.com/contentauth/c2pa-js/tree/main/packages/c2pa-node) and installed **@contentauth/c2pa-node 0.9.10** TypeScript declarations/Rust binding. Modern `Builder.withJsonAsync`, `Context`, `LocalSigner`, `Reader.fromAsset`, create/edit intents and `parentOf` ingredients. Native binaries support macOS ARM/Intel, Linux x64/ARM and Windows. Independent file binding and signer trust are distinct SDK results.
- [C2PA signing workflow](https://opensource.contentauthenticity.org/docs/tasks/build/) and SDK README: use ES256 credentials, record digital source type, preserve edit ingredients. Local demo certificates use temporary P-256 keys and SHA-256-signed root/leaf profiles; temporary private files are removed. They are never publicly trusted by default.
- [OpenAI Images guide](https://developers.openai.com/api/docs/guides/image-generation): Images API generation, explicit model, `b64_json`, PNG, one 1024px low-quality result. No automatic latest-model migration. Uses only the official API host; generic reasoning-provider URL does not redirect image-key credentials.
- [Unified thirdweb ERC-721 reference](https://portal.thirdweb.com/references/typescript/v5/erc721/claimTo) plus installed unified v5 read APIs. A generic open NFT Drop claim would bypass the credential gate. The implementation uses a custom ERC-721 credential drop with exact, expiring EIP-712 permits and thirdweb NFT reads, documented as an adaptation rather than a prebuilt deployment.
- [Official TypeSafe System One reference](https://docs.typesafe.ai/api/system-one): hosted `/v1/systemone`, named Choice questions, keyed answers and confidence. Existing adapter schema is retained. [Official Pinata v3 upload reference](https://docs.pinata.cloud/api-reference/endpoint/upload-a-file): bearer JWT, multipart file and explicit public network; independent IPFS gateway read-back verifies the uploaded bytes. Base network enforcement and Supabase durable private state reuse existing shared capabilities.

Decisions: image generation instead of clips; actual native SDK signing and inspection rather than a JSON sidecar renamed “C2PA”; deterministic non-model image grades create new signed edits; raw prompt stays in private project and only its SHA-256 is embedded. Public file inspection disables upload-controlled remote manifest/OCSP fetching. Pinata publication requires explicit consent. Contract stores file, manifest, model and parent commitments with immutable IPFS token URI. Creator wallet signs mint; unfunded verifier signs no blockchain transactions. No automatic network exception.

Limits: provider and signer attestations cannot prove truth/copyright or independently identify the human creator; a current configured trust-anchor policy is not proof of global public trust-list enrollment. Certificate revocation/expiry and timestamp policy require operator review. Public uploads require hosted admission and resource limits. Browser/Anvil/provider doubles are not production evidence.
